# Abyss 复杂任务闭环规则

适用于用户要求“完成全部开发”“完成验收”“做成可交付产品”“提交推送发版”的复杂任务。

## 不得因阶段成功停止

以下任何一个事件都只能视为检查点，不能视为任务完成：

- 子代理返回完成或后台命令成功；
- 定向测试通过；
- 静态分析通过；
- Flutter/CMake/安装器编译成功；
- 看到一个截图或窗口能启动；
- 代码已经提交到本地。

收到这些结果后，主代理必须检查计划剩余项、工作树、进程、日志和产物，继续下一个阶段。

## 完成门槛

复杂功能至少按以下顺序闭环：

1. 代码实现和主代理审查；
2. 相关定向测试；
3. 修改模块静态分析；
4. 实际运行新构建/隔离环境；
5. 真实界面操作和截图查看；
6. 交付构建及文件校验；
7. 用户要求提交时，提交、推送、远端分支核验；
8. 用户要求发版时，Release 创建、附件上传、远端大小/hash/target commit 核验。

不适用的阶段必须写明“不适用”；未执行的阶段必须写明“未验证”，不能用编译或测试结果代替。

## 停止条件

只有两种情况可以结束：

- 所有用户要求的完成门槛已经满足；
- 遇到明确外部阻塞，且已经记录：尝试过的命令、具体错误日志、已完成部分、未完成部分和下一步方案。

“预计时间到了”“子代理结束了”“测试通过了”都不是停止条件。

## 子代理与后台任务

- 委派必须写清范围、交付物和完成条件。
- “准备执行”“发现可以修复”“下一步会改”不是交付物。
- 每次后台任务结束后，主代理必须检查结果并继续整合；不得把后台成功通知当作最终报告。
- 同类错误重复出现时，收敛范围并由主代理接手，不得无限续派。

## 真实验收

- GUI功能必须使用新的、明确标识的构建目录；不能覆盖正在运行的发行目录。
- 必须看实际截图或等价的真实 UI 状态；不能只读取控件树或进程存在。
- 使用人工 fixture 时，必须说明它是人工/隔离数据，不冒充真实上游或真实付费模型验收。
- 主会话、项目文件、凭据和 BaoCode 必须保持隔离，不能为了验收读取或修改原版数据。

## 报告格式

最终报告必须区分：

- **已实现**；
- **定向测试**；
- **实际运行/GUI验收**；
- **构建和产物校验**；
- **提交/推送/Release**；
- **未验证或阻塞项**。

如果还有剩余项，报告标题不能写“全部完成”。
