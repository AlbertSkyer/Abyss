## 1. 产品定位

Abyss 是独立于 BaoCode 的多代理工作台：用户只与主代理对话，主代理负责拆解任务、管理成员、选择模型、接收结果和汇总交付。

从“按任务临时创建子代理”升级为“按需组建、持续复用的常驻代理团队”。团队可使用不同提供商的模型，以利用独立服务额度；不为了打满额度制造不必要的任务。

### 不变的约束

- Abyss 与原版 BaoCode 可以并行安装、同时运行；数据、会话、配置、任务和凭据独立。
- 使用外部 Claude Code CLI 执行主代理和子代理任务，不以内置内核替代开发或验收。
- 不修改或关闭原版 BaoCode，不读取或复制其凭据。
- 不覆盖正在运行的发行目录，不擅自删除旧包。
- 保持移植上游更新的能力，不向 upstream 推送产品分支。
- 用户只向主代理输入，成员详情保持只读，不提供子代理 composer 或直接发消息入口。

## 2. 常驻团队的含义

“常驻”指保留成员身份、职责、绑定模型和可续接上下文；成员完成一项任务后进入待命，后续相关工作优先交回该成员。

- 常驻不等于持续调用模型，不要求每个成员独立占用一个永久运行的进程。
- 待命时不周期性调用模型，不产生用于维持在线的心跳推理请求。
- 一个成员可连续承接多项工作；成员与任务不是同一个实体。
- 完成的任务是历史记录；成员待命是可继续派工的状态，界面必须区分。
- 默认团队归属于当前主会话，不自动跨主会话共享上下文。

### 2.1 按需组建

不在每个主会话启动时预先创建所有成员。主代理在确有需要时创建成员，并记录名称、职责和模型。

可采用实现、分析、审查等职责，但不把某一品牌或模型永久写死为某种职责，也不要求每个会话都拥有这三类成员。

### 2.2 复用与新建规则

派工优先顺序：

1. 查找职责匹配、已有相关上下文的成员。
2. 成员空闲且上下文适用时，优先续接原成员。
3. 成员忙碌且新任务独立、值得并行时，再考虑创建其他成员。
4. 无关领域、上下文过重或需要独立审查时，使用新成员或新上下文，并记录原因。

不因一次报错就立即抛弃成员。先区分请求故障、任务执行错误、上下文不适合与用户主动停止。

同一成员默认一次执行一项任务。相互依赖或可能修改同一资源的工作不能仅因有空闲模型就强行并行。

### 2.3 模型绑定

- 成员默认绑定创建时选择的提供商与模型，后续派工不频繁切换。
- 确需换模型时，优先创建替代成员，保留原成员历史，提供简短交接和替代关系。
- 不把新模型伪装成原成员的无损续接；展示哪些上下文来自交接摘要。
- 子任务模型选择不改变主会话模型。

## 3. 自动模式开关

设置中提供独立开关：**自动派工与选模**。

其作用范围是子代理创建、续接派工和模型分配，不是整个应用的工具权限。

| 项目 | 开启 | 关闭 |
| --- | --- | --- |
| 提出子任务 | 主代理决定 | 主代理提出 |
| 新建成员 | 在允许模型池和并发限制内自动创建 | 展示任务说明与模型选择，用户确认后创建 |
| 向待命成员继续派工 | 自动复用适合的成员，不弹窗 | 执行前展示任务说明、成员及绑定模型，用户确认后执行 |
| 选择模型 | 按本文调度规则自动选择 | 用户在审批中选择；已有成员默认绑定模型，换模型则明确创建替代成员 |
| 故障切换 | 允许在模型池内有限切换，留下原因和交接记录 | 不静默切换，执行前重新确认 |
| 取消 | 用户可随时停止；不得自动重启 | 取消审批不启动任务；不得绕过取消 |

### 3.1 默认与生效时机

- 本次确认的 Abyss 产品默认开启自动模式，用户可以关闭；只影响 Abyss，不改变 BaoCode 行为。
- 开关持久化到 Abyss 自己的设置中，重启后保留，并在主会话界面提供可见的当前模式标识和设置入口。
- 切换开关不终止已运行任务；对后续尚未授权执行的派工生效。
- 手动模式有待审批请求时开启自动模式，不自动批准已有请求；已有请求仍由用户确认或取消。
- 从自动切到手动后，尚未启动、未获授权的工作进入待审批；不能批量追认或重复启动。
- 历史审批不能作为今后所有任务的长期授权；自动执行的授权来源是当前开启的自动模式和允许模型池。

### 3.2 安全边界

**关闭子任务弹窗不等于关闭工具权限审批。**

文件删除、危险命令、外部发布等操作继续遵守应用及 CLI 的权限规则。自动模式不得扩大工具权限，也不得通过换成员、换模型或其他通道绕过拒绝。

新建和续接都必须处于可核验的调度边界内。如果外部 CLI 的续接路径不能可靠拦截、记录或遵守手动模式，就明确标记为不支持并阻止该操作，不能静默绕过，也不能改用内置内核冒充支持。

## 4. 模型池与自动选择

### 4.1 允许名单

子代理模型池是自动调度的允许名单，不是对所有已配置模型的隐式授权。

- 主代理只能选择池中已启用、可用于当前会话的模型。
- 不自动添加模型、创建 provider、借用 BaoCode 配置或修改凭据。
- 模型池为空或没有兼容模型时，不偷偷选择池外模型。主代理能自行完成则自行处理，否则说明阻塞并提示配置模型池。
- 删除或禁用池条目不强杀已经运行的任务；后续派工不再使用该条目，绑定该模型的待命成员暂停接单，直至用户恢复或按规则替换。
- 进程级强制子代理模型设置优先。必须显示实际限制；若强制模型不在允许名单或不符合当前分配，不能声称仍按自动选择执行。

### 4.2 选择原则

采用 **任务适配优先，兼顾速度和跨提供商并发**：

1. 优先利用职责匹配成员的已有上下文，避免不必要的重新阅读与交接。
2. 简单、明确、独立任务优先选择定位为快速的可用模型。
3. 复杂实现、难定位问题优先选择能力定位较高的可用模型。
4. 独立审查优先使用不同成员，适合时采用不同模型，且避免只把实现者的结论当作审查输入。
5. 多个独立任务尽量分散到不同提供商，避免集中争用一个提供商的额度。
6. 不能只凭模型名字猜测能力、速度、价格或独立限额，也不为追求分流牺牲明显的任务适配性。

### 4.3 可选能力标签

模型池允许填写可选标签，例如：快速、复杂任务、分析、实现、审查。

- 用户可以标注，但不强制填写；未填写也能使用自动模式。
- 标签是调度偏好，不是能力保证，也不保证每个任务类型都有专门模型。
- 无标签时，基于可获取的模型信息与已有执行记录保守选择；信息不足时不伪造评分或性能结论。
- 初期不要求自动基准测试，不额外产生用户未请求的付费评测请求。

### 4.4 并发规则

- 默认同时运行上限为 **3 个子任务**，可配置。
- 此上限是运行任务数，不是团队成员总数；待命成员不占运行名额。
- 只有任务真正独立且有并行收益时才并行，不强制始终保持满额。
- 队列中的任务仍需遵守当前自动/手动模式及模型可用性规则。
- 同一 provider 的多个模型不假定拥有独立额度；已知限流时尊重 provider 级等待与退避。
- 不把当前 CLI 接线“仅映射前 3 个池模型”的实现限制当作产品调度规则。允许名单容量与运行并发上限是两个不同概念；尚未支持的容量或路径必须明确展示。

## 5. 故障与停止规则

### 5.1 有限重试与故障切换

- 短暂网络错误：同模型有限重试，遵守服务端等待和退避提示。
- 持续限流或明确不可用：自动模式允许在名单内选择其他 provider/model，记录原因；需要替代成员时附交接说明。
- 任务执行错误：优先向原成员补充定位信息或由主代理接手，不把所有错误都当成模型故障。
- 无合适替代：报告主代理，由主代理自行处理或向用户说明阻塞。
- 重试及切换必须有有限的总尝试边界，计入 CLI/上游已进行的重试，不能通过不断新建成员获得无限重试。
- 具体重试次数与等待参数属于后续实现细节，但不得采用无界重试或循环切换。

### 5.2 用户停止优先

- 用户停止任务后，不得通过重试、续接、切换模型或新建成员自动重启同一工作。
- 明确区分未启动即取消、执行中停止、运行失败、成功完成和进程退出造成的中断。
- 取消与停止决议应持久化，应用重启后不能恢复为成功或普通执行失败。
- 用户停止任务不等于删除成员及其历史；后续重新派工需要新的明确任务，不能把停止当作暂时网络错误。

## 6. 可见性与界面

### 6.1 主会话

自动模式不弹子任务确认框，但派工不应隐形发生。

展示简短动态，例如：

> 已交给“实现成员”，使用模型池中的 DeepSeek；复用该成员的相关上下文。

详情记录任务说明、成员、提供商、请求模型、分配模型、可获得的实际响应模型、选择原因、起止时间、状态以及切换记录。实际模型未知时明确显示未知，不拿分配模型冒充实际模型。

不把完整子代理对话自动灌入主会话；由主代理接收真实报告后汇总。未收到报告不得预测或捏造完成结果。

### 6.2 侧栏与只读详情

- 整体会话栏可折叠，显隐与宽度偏好持久化。
- 设置中提供独立开关：**显示左侧子代理列表**，默认关闭；偏好保存到 Abyss 自己的设置中，重启后保留。
- 开关关闭时，左侧只显示主会话，不显示其子代理成员、子任务分组及关联历史条目；不影响其他已有会话类型。
- 开关开启时，在每个主会话下展示成员及关联任务历史，分组独立折叠；折叠后保留运行、待审批和未读提示，待命与运行清晰区分。
- 该开关只控制列表显示，与“自动派工与选模”、整体侧栏折叠和各主会话子分组折叠相互独立；切换时保留原有分组折叠偏好。
- 隐藏列表不停止或禁用子代理，不清除历史、未读状态或成员上下文，也不改变审批行为。主会话中的派工动态、结果汇总和任务详情入口仍可使用。
- 成员详情和任务详情只读，没有 composer，不提供直接给子代理发消息的入口。
- 用户可以停止运行任务、禁用成员；不把“查看详情”误做成启动或恢复执行。
- 现有可写的 /btw 或 fork 会话与团队成员明确区分，不能作为绕过只读边界的入口。

### 6.3 游戏引擎编辑器式工作区

Abyss 的界面控制体验以 Unity、Unreal 等编辑器为参考：所有主要功能都有统一入口，主要界面作为可管理、可自由布局的面板存在。既支持只保留主会话的简单使用，也支持多代理开发控制台，不要求用户始终使用复杂布局。

“窗口”包括主窗口内的停靠面板、同一区域的标签页，以及可拖出主窗口的独立浮动窗口。**浮动窗口与多显示器使用是明确产品目标，不仅限于主窗口内部拖动。** 不把每个按钮都做成独立系统窗口；权限审批、确认删除、文件选择等短暂交互仍可使用对话框。

### 6.4 统一“窗口”入口

顶部左上方提供菜单入口，建议整体结构为“文件、编辑、查看、窗口、帮助”。其中“窗口”是全部主要功能面板的可发现入口，不依赖用户记住快捷键或当前布局。

窗口菜单按功能分组，目标入口包括：

- 会话：会话列表、主会话、会话历史。
- 代理：代理团队、任务队列、只读成员与任务详情。
- 开发：文件浏览器、代码编辑器、终端、Git 与变更。
- 运行与诊断：日志、模型用量。
- 设置：应用设置与相关配置面板。
- 工作区布局：布局预设、保存当前布局、切换已保存布局、重置布局、找回浮动窗口。

上述是目标功能分类，不代表每个面板已经实现。后续新增主要功能也必须提供可发现的窗口入口。菜单动作应明确区分打开/聚焦现有面板与新建实例，不能因重复打开而意外重复启动会话或任务。

面板被关闭后始终能够从窗口菜单重新打开；对于尚需选择具体会话、成员或任务的详情入口，应提供选择或导航，而不是创建无归属内容。

### 6.5 自由停靠、标签与浮动窗口

- 拖动面板标题或标签调整位置；停靠时提供明确的落点提示。
- 支持区域上、下、左、右拆分，拖动分隔线调整大小。
- 支持将多个面板合并为标签组，切换标签及调整标签顺序。
- 支持临时最大化单个面板，并恢复之前布局。
- 支持将面板拖出主窗口形成独立浮动窗口，移动至其他显示器，并重新停靠回主窗口。
- 浮动窗口可以关闭；关闭只移除该展示入口，之后可从窗口菜单找回。
- 保存停靠树、标签顺序、活动标签、面板尺寸与可见性、浮动窗口位置和尺寸等布局状态；重启后恢复。
- 显示器移除、分辨率或缩放变化时，将不可见的浮动窗口恢复到可用屏幕范围，并提供显式“找回浮动窗口”操作。
- 正确处理浮动窗口的焦点、快捷键和权限弹窗归属，避免同一快捷键重复触发、输入落入错误会话或审批窗口无法找到。

### 6.6 布局与业务生命周期分离

- 关闭面板、切换标签、移动、拆分、浮动或切换布局，不停止后台任务，不重启 CLI，不重新发送消息或执行工具。
- 多个入口查看同一成员或任务时共享真实业务状态，不重复创建执行实体。
- 停止任务必须是明确的停止操作，不能隐含在关闭任务详情或代理团队面板中。
- 主窗口隐藏与整个应用退出仍按第 7 节区分；浮动窗口的关闭不等于退出应用。
- 左侧子代理列表开关继续默认关闭。独立“代理团队”面板可从窗口菜单打开，打开该面板不强制开启左侧列表，关闭左侧列表也不关闭该面板。
- 面板位置不改变权限：成员和任务详情即使浮动、重新停靠，仍保持只读。

### 6.7 布局预设与恢复

提供以下初始布局，并允许用户调整后另存为自定义布局：

- 专注对话：主会话为主，其他面板隐藏。
- 多代理协作：主会话、代理团队、任务队列、只读任务详情。
- 代码开发：文件浏览器、代码编辑器、主会话、终端、Git。
- 运行诊断：主会话、任务、日志、模型用量。

始终提供可访问的“重置布局”，避免面板被拖乱、尺寸过小或移出屏幕后无法恢复。布局恢复失败时回退到可用的默认布局，不因此丢弃会话、成员或任务历史。

### 6.8 多会话标签页与同时可见

会话像编辑器中的文件一样以标签页打开，并可分组、分屏和浮动。**多个会话同时可见是核心需求，与多标签一起交付，不仅实现一次只能看一个会话的标签切换。**

#### 打开与导航

- 左侧单击会话：在当前聚焦的标签组查看，优先复用该组的预览标签，不因连续浏览而不断新增固定标签。
- 右键“在新标签页打开”：保留当前页面，在当前标签组新增固定标签并激活；不替换原标签内容。
- 右键“在右侧打开”：在右侧标签组打开；没有右侧组时创建分屏，使两个不同会话同时可见。
- 双击会话：固定为标签，不再被后续单击预览替换。
- 单个对话标签支持拖动排序、跨组移动，可停靠到主窗口内容区整体或任意分组的上/下/左/右，并与文件、终端等工具面板合并成同一标签组；不是只允许拖动整个“会话工作区”容器。会话与工具位置由同一停靠树管理。
- 原生浮动能力完成后，支持将单个对话拖出主窗口及重新停靠；2026-11-16 本批仅主窗口内停靠，不把系统浮动窗口计为已实现。
- “窗口”菜单提供会话面板及已打开会话的导航入口，关闭标签后仍可从会话列表重新打开。

#### 预览标签与草稿保护

- 每个标签组最多一个临时预览标签；浏览其他会话时可以替换该预览。
- 双击、明确选择新标签页或开始输入时，将预览标签固定。
- 不得通过预览替换、关闭标签、拖动或布局切换丢弃未发送草稿；有草稿的预览必须先固定，关闭后草稿仍归属于原会话并可恢复。
- 每个会话保留独立草稿、滚动位置和阅读状态，切换回来时恢复，不把其他会话的输入或位置带过来。

#### 唯一性与执行边界

- 同一会话默认只打开一个标签，按稳定会话身份去重；再次打开时聚焦既有标签，不创建第二个会话或 CLI。
- “在右侧打开”若目标会话已打开，则将既有标签移至右侧组，而不是复制执行实体；移动不能丢失草稿或滚动位置。
- 同会话双视图不是本轮默认能力；如以后增加，应作为明确的“复制视图”操作，并与新建会话、新标签页区分。
- 关闭标签只关闭展示，不停止会话及其后台任务；停止必须使用明确操作。
- 后台标签显示运行、待审批或未读等状态；结果归属原会话，不因焦点变化而混入其他会话。
- 分屏与浮动时，输入、发送、停止、快捷键及审批准确归属于当前目标会话；焦点必须清晰可见，不允许误发、重复发送或停止错误任务。
- 标签页、分屏布局、活动标签与相关视图状态随工作区恢复；恢复展示不自动重新发送消息、启动任务或重复调用模型。
- 主会话可以编辑，子代理成员及任务详情仍只读；成为标签页不改变权限边界。

### 6.9 任务控制台与执行可信度

自由布局服务于可靠执行，不以增加面板数量代替任务管理。优先做到“派得对、接得住、看得清、停得下、找得回”。

#### 任务卡与验收证据

- 正式任务使用轻量任务卡，包含目标、完成条件、负责人及关联成员、依赖、阻塞、改动、产物与验收结果。
- 主会话、任务队列、成员详情和执行记录引用同一任务实体，不各自维护互不关联的副本。
- 区分代理自报完成、改动已产生、定向测试通过和实际产品验收通过；执行状态与验证证据分开记录，不用统一“已完成”掩盖未验收项。
- 验证失败、跳过及未验证项目明确可见，主代理据此决定返工或交付。

#### 工作范围与并行冲突

- 派工时记录工作范围，例如目录、模块、目标文件及是否允许修改。
- 多个成员拟修改重叠文件时，向主代理提示，由其协调、调整范围或安排先后执行；不能无提示地并发覆盖。
- 显式记录任务依赖，未满足依赖的任务不得仅因有空闲模型而启动。
- 有必要时使用独立工作树等隔离方式，但小任务不强制创建隔离环境。
- 首期采用范围可见与冲突提示，不扩展成复杂分布式锁；范围声明也不能被宣传为严格的文件写入安全隔离。

#### 进展与阻塞

- 不只显示“运行中”，还显示有证据的阶段，例如定位、修改、测试、等待权限及外部服务阻塞。
- 检查点汇报实际进展、产物或明确阻塞，“准备执行”不能作为产出或完成证据。
- 正常耗时继续等待；具体阻塞明确说明；缺少进展迹象时检查进程、日志和产物，必要时由主代理收敛任务或接手，不仅按估时到点停止。
- 避免成员反复无产物汇报、主代理反复原样续派；用户停止优先，检查点不得自动复活已停止任务。

#### 当前操作对象

- 每个会话面板始终清晰标识项目、会话名称、主模型与自动/手动模式。
- 聚焦区域提供清晰但不刺眼的视觉提示；输入、发送、停止与快捷键绑定正确会话。
- 审批显示所属会话，多分屏与多显示器下也不能误发、误停、重复执行或把审批发给错误对象。

#### 基于事实的调度记录

- 在本地积累已有任务的执行记录，例如任务类型、耗时、成功/失败、限流、切换及明确的返工情况，用于辅助后续调度。
- 不额外产生付费排名请求，不把少量样本、端到端耗时或主观评价包装成可靠模型能力排名。
- 参考记录时区分任务类型、样本数量与 provider 状态；不虚构精确的能力总分或因果结论。
- 执行记录是调度辅助信息，不自动改变用户的允许模型池或能力标签。

#### 可追溯但不打扰

- 提供可停靠的“执行记录”面板，并纳入“窗口 → 运行与诊断”入口。
- 记录派给哪个成员、选择哪个模型、为什么新建而非复用、重试/切换原因、实际文件改动和验收证据。
- 主会话只显示简短动态，需要时再查看详情；选择依据和执行事实可追溯，不要求展示模型内部思考过程。
- 执行记录不保存密钥或完整敏感配置；不能把发送到模型的所有内容无差别复制进审计展示。

### 6.10 后续方向与范围控制

项目级团队偏好作为后续方向：不同项目可以保存各自模型池、职责偏好和布局，但不自动跨项目共享上下文。项目级规则的优先级与配置方式需在该阶段明确，不在本轮隐式实现。

当前不扩展插件市场、复杂可视化工作流设计器等大功能。优先顺序是：任务与验收状态清楚；工作范围、阻塞和冲突可见；多会话下不误发、不误停、不重复执行。

## 7. 生命周期与持久化

### 7.1 关闭窗口

关闭主窗口但应用仍在后台时，运行中的任务继续执行；完成后结果返回主代理，重新打开可查看成员、任务及未读状态。

### 7.2 退出或崩溃

不承诺整个应用退出或崩溃后任务仍在运行。重启后：

- 恢复成员身份、职责、模型绑定、关联任务、停止决议和可浏览历史。
- 原运行任务需要核实状态；无法确认存活时标为中断或待核实，不能假装仍运行或已经完成。
- 不自动重跑可能产生副作用的中断任务。
- 续接原成员必须验证外部 CLI 上下文是否可恢复；不可恢复时明确说明，通过交接创建替代成员，不冒充无损恢复。
- 恢复历史本身不触发模型调用。

需要保存的核心关联为：主会话 → 成员 → 多项任务；成员 ID、任务 ID 与 CLI agent/session 标识不能混为同一个值。

## 8. 验收标准

验收区分定向测试、真实 CLI 协议测试、交付包真实界面与上游执行，不互相替代。

| 场景 | 通过标准 |
| --- | --- |
| 任务卡与证据 | 多入口引用同一任务；目标、依赖、产物及验证结果可查，自报完成不冒充验收通过 |
| 范围与冲突 | 重叠修改向主代理提示，依赖任务不抢跑，必要隔离不被宣传为默认严格隔离 |
| 进展检查点 | 阶段和阻塞有事实依据，无产物汇报不算完成，异常时检查并收敛，不无界续派 |
| 执行记录 | 成员/模型选择、新建、重试、切换、改动和验收可追溯，不泄露密钥或内部思考过程 |
| 调度事实记录 | 仅利用已有执行数据，不暗中运行付费评测，不制造精确能力排名或扩大模型名单 |
| 自动模式 | 池内自动选模、自动创建/续接，无子任务审批弹窗；分配及理由可见 |
| 手动模式 | 新建与续接派工均执行前确认，取消不执行，并发请求不覆盖 |
| 开关切换 | 偏好持久化；不终止已运行任务，不隐式批准已有弹窗，不重复启动 |
| 成员复用 | 连续两项相关任务由同一成员续接，能验证真实身份与上下文延续，不只是 UI 复用名称 |
| 待命 | 完成任务后进入待命，无维持在线的重复模型请求；之后可再次接单 |
| 新成员边界 | 无关任务或独立审查按规则使用新上下文，记录原因 |
| 跨提供商并发 | 两个获批或自动授权的独立任务实际运行区间重叠，实际路由与分配一致，主模型不变 |
| 并发上限 | 默认最多 3 个运行中任务，其他任务排队；待命成员不占名额 |
| 故障切换 | 仅限池内、有限尝试、原因可见，真实执行错误不被一律当成模型不可用 |
| 用户停止 | 停止后不通过新成员、续接或模型切换重启；重启应用后决议仍有效 |
| 左侧子代理列表开关 | 默认关闭；开启后显示成员及任务分组，关闭后隐藏；重启保留，切换不影响执行、审批、历史、未读与分组折叠偏好，主会话任务详情入口仍可使用 |
| 只读边界 | 仅主代理可向成员派工，成员和任务详情无输入框 |
| 窗口生命周期 | 隐藏窗口后任务继续，重开结果返回；与应用退出明确区分 |
| 重启恢复 | 团队及历史可浏览，任务状态真实，不误报成功、不自动重跑副作用任务 |
| 权限与隔离 | 自动模式不绕过工具权限，Abyss 不影响原版 BaoCode、不借用凭据 |
| 统一窗口入口 | 主要功能面板均可从左上方“窗口”菜单打开或聚焦；关闭后可找回，不意外创建重复会话或任务 |
| 多会话标签与分屏 | 右键新标签保留原页面，右侧打开可同时查看不同会话；支持标签排序、跨组移动及上下左右分屏 |
| 预览与草稿保护 | 单击复用预览，双击或输入后固定；替换、关闭、移动及恢复布局不丢草稿，各会话滚动位置独立 |
| 会话唯一性与焦点 | 重复打开定位已有标签，右侧打开移动已有标签而不重复启动 CLI；发送、停止和审批不串会话，关闭标签不停止后台任务 |
| 自由布局 | 面板可拖动停靠、上下左右拆分、合并标签、调整尺寸和临时最大化，再恢复布局 |
| 浮动与多显示器 | 面板可拖出主窗口、移至第二显示器并重新停靠；焦点、快捷键及审批归属正确 |
| 布局持久化与找回 | 重启恢复面板及浮动位置；移除显示器后窗口仍可找回；支持布局预设、自定义保存和重置 |
| 界面与业务解耦 | 关闭、移动面板及切换布局不重启 CLI、不重复调用、不停止任务；浮动详情仍只读，代理团队面板与左侧列表开关独立 |

只运行与本轮改动有关的测试，不为此随意运行完整套件。构建通过不等于真实 GUI 或上游流程通过。

## 9. 开发顺序

1. 盘点真实外部 CLI 的成员续接能力，验证上下文延续、模型绑定以及创建/续接的权限边界；不以 UI 任务记录代替证明。
2. 区分成员与任务数据模型，补齐任务卡、依赖、验收证据、持久化及取消/停止恢复语义。
3. 实现自动模式开关及手动模式兼容，明确切换时待处理请求的行为。
4. 接入允许模型池、可选标签、模型选择、并发队列与有限故障切换。
5. 调整侧栏成员/任务结构、待命状态、只读详情和执行记录；加入范围冲突提示、实际进展及阻塞检查点，逐步积累调度事实记录。
6. 使用小规模真实任务验收成员复用、跨 provider 并发和窗口/重启行为，分别记录通过项、失败项及未验证项。

界面工作区按以下顺序推进，复用现有会话、任务和编辑器逻辑，不借机重写全部功能：

1. 统一入口：建立“窗口”菜单，现有主要功能可打开、聚焦和找回。
2. 统一面板与多会话：接入停靠、会话标签组、右键新标签/右侧打开、预览与固定、区域拆分及布局持久化；同时交付不同会话分屏可见，保护草稿、焦点和会话唯一性，确保界面生命周期不驱动业务重启。
3. 布局管理：提供布局预设、自定义保存、切换、重置和临时最大化。
4. 浮动与多屏：实现独立浮动、跨显示器、重新停靠、焦点与快捷键、离屏窗口找回。
5. 分别验收界面布局和真实代理执行，重点验证移动/关闭面板不会造成重复执行或状态丢失。阶段性交付不得被表述为已完成浮动与多屏最终目标。

本次只确认并记录产品目标；文档落地不代表上述开发步骤已经完成。
